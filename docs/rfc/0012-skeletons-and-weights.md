# RFC 0012: Скелеты, редактирование костей и автогенерация весов

- Статус: draft
- Автор: владелец (записано агентом 2026-11-09)
- Дата: 2026-11-09
- Влияет на: `core/mb_mesh_data.gd`, `core/mb_mesh.gd`, `editor/*` (гизмо, сессии, тулбар, бинды),
  `commands/*`, `mesh_ops/*` (перенос весов при операциях), `shapes/*` (скейлинг параметров под скиннинг),
  `docs/README.ru.md`, `docs/README.en.md`, `dist/listing.md` (отдельный гейт)

## Что решили (черновик)

В планах: работа со скелетом прямо в редакторе — создание костей, правка иерархии и rest-положения,
привязка меша к скелету и автогенерация весов. Плагин сейчас умеет только геометрию; скиннинг (скелет +
веса) — новый класс задач, и он расширяет назначение плагина: «моделирование пропов» становится
«моделирование пропов вместе с их скелетом». Это надо будет учесть в листинге стора (отдельный гейт).

Кода нет. Ниже — что уже известно про данные и где будут ловушки, чтобы реализация не начиналась с нуля.

## Факты, на которые опирается решение (по коду 2026-11-09)

- `MBMesh extends MeshInstance3D`, геометрию собирает `rebuild()` из `MBMeshData.to_array_meshes()`; при
  >256 поверхностях остаток уходит в внутренние `MeshInstance3D`-чанки (`_overflow_chunks`) — скин и
  скелетное отношение придётся вешать и на них.
- `MBMeshData.positions` хранит СВОЮ копию угла на каждую грань. Связность ищется по квантованным
  координатам (`Vector3i(roundi(p * 10000))`), не по индексам (RFC 0010). Значит и веса — атрибут
  **позиции по координатам**, а не индекса: двойники одной точки обязаны получить одинаковые веса, иначе
  шов разъедется при анимации.
- Тот же приём уже используется: `colors` — цвет по позиции, `sharp_edges` — пара квантованных точек.
  Веса логично делать так же (у пары «позиция → влияния»), а не сырым `PackedFloat32Array` по индексам.
- Undo — снапшот данных меша (`MBCommand.copy_mesh_data()`), каждый шаг правки геометрии/цвета = один
  шаг отмены. Веса, положенные в `MBMeshData`, попадают под тот же механизм бесплатно; кости, живущие на
  узле `Skeleton3D`, — нет, для них нужна своя команда.
- Движковый рендер скиннинга требует `ARRAY_BONES` (4 индекса на вершину) и `ARRAY_WEIGHTS` (4 веса) в
  `ArrayMesh` плюс `Skin` на `MeshInstance3D`; больше 4 влияний на вершину Godot не возьмёт.
- `rebuild_positions()` — быстрый путь для таскания вершин; если веса меняются, он должен либо веса не
  трогать, либо пересобирать их тоже.

## Открытые вопросы (решать до кода)

1. **Где живёт скелет.** `Skeleton3D` в сцене (движковый, сразу анимируется, но правки костей — вне
   снапшота `MBMeshData`) против костей внутри `MBMeshData` (редактируемо и откатываемо, но нужен код
   синхронизации со сценой). Черновик склоняется к «скелет — узел сцены, веса — в данных меша».
2. **Формат весов.** Свойство меша `skin_weights` + `skin_bones` в `MBMeshData` (биндинги `Skin`) против
   массива влияний по квантованной позиции. Нужно решение по сериализации в `.tres` и по стабильности при
   save/load.
3. **Автогенерация весов — каким методом.** Встроенного в Godot нет. Кандидаты: оболочки костей (расстояние
   до отрезка кости с затуханием, дёшево и предсказуемо, но швы у суставов грубые); воксельная диффузия /
   «тепловой» решатель по поверхности меша (лучше на суставах, дороже и капризнее на тонких деталях);
   гибрид — оболочки + сглаживание весов по сварке. Нормализация и отсечение верхних 4 влияний — по умолчанию.
4. **Иерархия и rest.** Как задаются кости: кликом по мешу с автоподбором направления, рисованием
   «цепочки» или импортом из уже существующего `Skeleton3D`? Нужно ли править rest-положение после
   генерации весов (перегенерация при сдвиге кости).
5. **Зеркало.** `mirror_enabled`/`mirror_axis` живут в данных, `Apply Mirror` печёт геометрию: веса
   зеркальных граней должны зеркалиться на одноимённые кости с противоположной стороны (имена вида
   `arm.L`/`arm.R`). Правило именования надо зафиксировать.
6. **Операции топологии.** Extrude / bevel / knife / Merge by Distance / CSG-бейк создают новые позиции.
   Новые точки должны наследовать веса исходных (через `_cut_position(..., owner)`/квантованный ключ);
   CSG-бейк — веса ближайшей исходной вершины. Без этого скиннинг «рвётся» после любой правки геометрии.
7. **Экспорт в игру.** Экспорт в файл (PBM/GLB) выпилен и не возвращается — значит скиннинг работает на
   уровне сцены Godot: меш-узел + `Skeleton3D` + `Skin` едут в сцену как есть. Что именно сохранять в
   `.tscn`, а что держать только в `MBMeshData`, — вопрос к формату узлов.

- [ ] автогенерация весов + нормализация, отсечение 4 влияний, сглаживание;
- [ ] перенос весов при операциях меша и при `Apply Mirror`;
- [ ] баннер-отчёт вместо Output (сколько точек без весов, максимум влияний, кости вне меша);

## Последствия

- Правило `AGENTS.md` «каждая правка геометрии/цвета — один undo-шаг» распространяется и на веса; правка
  костей на узле — тоже свой шаг.
- Открытая вкладка: скиннинг — не «моделирование» в узком смысле; листинг стора и README придётся
  переписать, когда появится код.

## Проверка (когда будет код)

- меш + скелет из двух-трёх костей анимируются в редакторе без разъезда швов (проверить на сваренных
  гранях и на меше после extrude);
- веса переживают save/load сцены и undo/redo;
- при `Apply Mirror` левая и правая половины гнутся зеркально;
- живая проверка UI — в редакторе через MCP (`godot-mcp-authoring`), в изолированной копии проекта.
